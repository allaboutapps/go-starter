## 26.08.0 - 2026-08-20
### Changed
* **BREAKING** Bump Postgres from `postgres:17.4-alpine` to `postgres:18.6-alpine`
  - **A Postgres 18 server cannot read a Postgres 17 data directory. There is no in-place upgrade path — a running deployment needs an explicit `pg_upgrade` or a dump/restore, and skipping this leaves the database refusing to start.**
  - In addition, the official Postgres image changed its data layout in 18: `PGDATA` moved from `/var/lib/postgresql/data` to `/var/lib/postgresql/<major>/docker`, and the declared `VOLUME` moved from `/var/lib/postgresql/data` to `/var/lib/postgresql`. Our `docker-compose.yml` was updated accordingly (`pgvolume:/var/lib/postgresql`).
  - **If you keep the old `pgvolume:/var/lib/postgresql/data` mount, Postgres 18 still starts up perfectly happily — but it writes to an anonymous volume instead, so it comes up with an empty database and every write is silently discarded on the next `docker compose down`.** This failure mode is easy to miss because nothing errors.
  - Before rolling out this change:
    - **Local development**: run `docker compose down -v` *before* rebuilding. Your local database is recreated from scratch; run `make sql-reset && make sql-spec-reset && make sql-spec-migrate && make all` afterwards. If you kept anything valuable in your local database, dump it first with `pg_dump`.
    - **Live / staging**: plan the major upgrade explicitly (`pg_upgrade` or dump/restore), and verify your managed-database provider actually offers Postgres 18 before merging.
    - If you deliberately want to stay on Postgres 17 for now, pin `postgres:17.11-alpine` and `postgresql-client-17` and keep the `pgvolume:/var/lib/postgresql/data` mount — but note the mount path and the client version must match the server major you choose.
  - **Full step-by-step instructions (local, live, and how to verify the volume is actually wired up): [docs/migration-guides/postgres-17-to-18.md](docs/migration-guides/postgres-17-to-18.md)**
  - See the official Postgres release notes for the intermediate majors: https://www.postgresql.org/docs/release/18.0/
* **BREAKING** Migrate off the deprecated `github.com/go-openapi/swag` root package
  - `swag` v0.29 split its root package into per-concern submodules and **deprecated every top-level export**. There is no announced removal date (the root package is frozen for backwards compatibility), but it receives no new features, and go-swagger's generated code has already moved to the submodules.
  - All call sites in this repo were migrated (~85):
    - `swag.String` / `Int` / `Int32` / `Int64` / `Bool` / `Float64` / `Time` → `conv.Pointer`
    - `swag.StringValue` / `BoolValue` / `Float64Value` → `conv.Value`
    - `swag.ReadJSON` / `WriteJSON` → `jsonutils.ReadJSON` / `jsonutils.WriteJSON`
  - `github.com/go-openapi/strfmt/conv` was **dropped entirely** rather than aliased. We only used its `UUID4` and `DateTime` pointer helpers, and the generic `conv.Pointer[T]` from `github.com/go-openapi/swag/conv` subsumes both. This keeps a single unaliased `conv` import.
  - **Application code that uses any of these helpers will no longer compile as-is and needs the same treatment.** The mapping above is mechanical and the compiler will point at every site. Watch out for untyped numeric constants: `swag.Int64(3600)` becomes `conv.Pointer(int64(3600))`, since `conv.Pointer(3600)` infers `*int`.
  - **Full migration guide, including the complete 124-symbol mapping table, a `gofmt -r` recipe and the untyped-constant gotcha: [docs/migration-guides/swag-root-package-to-submodules.md](docs/migration-guides/swag-root-package-to-submodules.md)**
  - The scaffold templates in `scripts/internal/scaffold` emit the new API too, so newly scaffolded handlers stay valid.
* **BREAKING** Re-forked our go-swagger server templates in `api/templates/server` from upstream v0.36.4
  - `builder.gotmpl` and `parameter.gotmpl` are forks of upstream templates that had not been refreshed since Feb/Jun 2020. They no longer work with the current generator: the `comment` and `blockcomment` template functions were replaced by `lineComment` / `blockComment` (with different semantics — `blockComment` now emits the `/* */` wrapper itself, which produced nested, invalid comments), and parameter docs moved from block to line comments.
  - Rather than patching a 6-year-old fork, both were rebased onto the upstream v0.36.4 templates with only our customizations re-applied, each marked with `BEGIN/END CUSTOM BY AAA` and now documented inline:
    - the `query` / `param` / `form` struct tags, needed because we bind through `echo.DefaultBinder` rather than go-swagger's generated server
    - the standalone `Validate(strfmt.Registry) error` method, which is what makes the generated `Params` types satisfy `go-openapi/runtime.Validatable` — the interface every `internal/util.BindAndValidate*` helper accepts
    - the supporting `customsliceparamvalidator` / nullable / recursive-array validation plumbing
  - **If your project has its own modifications to these two templates, they are not preserved — diff your versions against the pre-upgrade files and re-apply your changes on top of the new upstream base.** Run `make swagger` afterwards and review the diff in `internal/types/`.
  - **Instructions for re-applying your own template changes: [docs/migration-guides/go-swagger-and-golangci-lint.md](docs/migration-guides/go-swagger-and-golangci-lint.md)**
  - The stock `BindRequest` is still generated but remains unused by this project.

### Fixed
* **`make test` silently exited 0 when tests failed** — CI would report green on a red test suite
  - The `test` target opts out of the global `SHELL = /app/rksh` wrapper via a per-target `SHELL` / `.SHELLFLAGS` override. Because the Makefile sets `.ONESHELL:`, the entire recipe runs as a *single* shell invocation, so with a plain `-c` the exit status reported to make is the status of the **last** recipe line (`go-test-print-coverage`) — a failing `go-test-by-pkg` was swallowed.
  - The flags are now `-cEeuo pipefail`, matching the "normal POSIX bash shell mode" already documented at the bottom of the Makefile.
  - **If you are on a version of this template that contains the broken override, your test pipeline may have been passing over failing tests. Re-run `make test` after upgrading and check for failures that were previously hidden.**
### Security
* Bump `google.golang.org/grpc` and `golang.org/x/mod` to clear vulnerability scanner findings
  - [`google.golang.org/grpc` v1.79.3 → v1.83.1](https://github.com/grpc/grpc-go/releases/tag/v1.83.1) fixes [GO-2026-6061](https://pkg.go.dev/vuln/GO-2026-6061) (xDS RBAC authorization engine and HTTP/2 transport server). `govulncheck` reported this one as **reachable** from our code.
  - `golang.org/x/mod` v0.37.0 → v0.40.0 fixes CVE-2026-56864 and CVE-2026-56865, where a malicious `GOSUMDB` / `GOPROXY` could serve or forge module content. Not reachable from our code, so `govulncheck` stayed quiet — but `make trivy` scans `go.mod` directly and failed on them.
  - Both pull transitive dependencies forward: `google.golang.org/api`, `golang.org/x/crypto`, `golang.org/x/net`, `golang.org/x/text`, `golang.org/x/tools` and `google.golang.org/protobuf`.
  - One advisory remains reported by `govulncheck` at module level and is knowingly not actioned: [GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932) flags `golang.org/x/crypto/openpgp` as unmaintained. We do not import that package, and `golang.org/x/crypto` is already at its latest release.
